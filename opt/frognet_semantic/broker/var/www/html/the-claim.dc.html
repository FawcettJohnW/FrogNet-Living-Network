Two defaults, and where they flip

Two choices the field made for good reasons — and the case where the tradeoff turns over.

UDP for live media, and messages as the way to network — both were the right defaults for the links they were chosen on, and most of the time they still are. FrogNet takes the other side of each. Not because the field was wrong — because on a real degrading link the tradeoff flips. Here's the reasoning, and the tape you can check it against.

The default · media

Live media rides UDP.

RTP, WebRTC, and SIP spray packets and salvage the wreckage because, on most links, best-effort delivery beats waiting on a retransmit — and TCP's head-of-line blocking is a real cost: one stalled segment holds up everything queued behind it. That is a good default, and we're not pretending it isn't.

Where it flips: we run live media on TCP and defuse head-of-line blocking at the source. Under buffer pressure the sender drops whole frames before they are ever queued, so what's in flight is always the freshest frames delivered intact — never a backlog of stale ones stuck behind a retransmit. No half-frame to salvage: clean frame, or clean omission.

The tradeoffOn a badly degrading link this stays watchable where best-effort corrupts — the picture thins instead of shattering. The better side of the tradeoff for integrity-critical live media; not a claim UDP is obsolete.
The default · coordination

Network programming means passing messages.

Requests, replies, acknowledgments, retries, renegotiation — the whole discipline manages an exchange that has to reassert itself the moment something fails. The transport underneath advanced enormously; the model we program it in did not. It's how nearly everything on the wire is written, and for good reason.

Where it flips: FrogNet coordinates through shared memory instead — Gelernter's tuple spaces, carried to the wide area (lineage on the compare page; the model is specified in Magnum Croakus § 22). You write a value where you compute it and read it where you need it; changing call quality isn't a renegotiated session, it's a memory write the far side simply reads.

The tradeoffNo session to fall off a cliff: the media ladder steps from HD to a heartbeat and back with no redial, because there was never a connection to renegotiate — only a value that changed.

The result — and what it isn't

Clean audio and video that self-adjusts over a real 900 MHz link as it's starved and recovers — with no redial. The headline isn't the bitrate; modern codecs hit low bitrates every day. It's the behavior under changing conditions — it degrades and climbs back on its own, because quality is a value the network holds, not a session it has to rebuild.

§Scope, up front

FrogNet and the Internet.

Before the objection writes itself: FrogNet does not replace the Internet, and it does not wall you off from it. It's a private network layer that runs alongside the public web — and yes, both ends run FrogNet. That isn't a limitation to explain away; it's the whole point.

What it is

A private layer beside the Internet.

Local devices join the FrogNet; the FrogNet reaches the Internet — directly, or through another FrogNet acting as the gateway. Traffic addressed to the private 10.x network rides the adaptive FrogNet node; everything else routes straight out, at normal speed. The address decides — and if you already run your own 10.x network, FrogNet coexists without interfering; its nodes just need unique addresses.

SoBoth at once, all the time — public sites and FrogNet services side by side, neither one taxing the other.
What it is not

A way to optimize the whole Internet.

The gains here — semantic compression, the adaptive wire, custom handlers — need a cooperating FrogNet on both ends. Talk to an ordinary public server with no FrogNet on it and you reach it fine, but as plain HTTP, with none of the advantages. And a FrogNet's size is bounded by its hardware — most of all the elected database host that holds the shared memory.

SoInfrastructure for a network you own on both sides, honestly bounded — not a client for someone else's.

§The evidence

Two first runs. Unedited.

Not a rehearsed demo reel — the actual experiments, recorded as they happened, narrated in real time. One establishes the baseline; one starves the link and watches the ladder move.

Baseline. HD video holding over the 900 MHz link — 1280×720 at 22 fps, bidirectional, no delay — with the did-vs-would counter reading ~89% of the bytes never sent.†

† A did-vs-would estimate against published WebRTC bandwidth for the same session, not a packet capture.

The ladder. The link is starved live — 987 → 637 → 450 kbps — audio holding priority as the picture thins, then a clean climb back to full frame rate. No reconnect. No redial.

Video files land in media/ at deploy; the branded first-run frames stand in until then.

Check it yourself

We'd rather be reproduced than believed.

Filing this under something you already know — CRDTs, Reticulum, an overlay, a tuple space? The honest map takes each in turn and says where the resemblance is real. And the protocol underneath is being written up as an open specification, so the wire becomes a contract you can implement against — not a black box you're asked to trust. Where that's headed →

We state the efficiency honestly: against a competently written message protocol, the shared-memory wire runs about 3.4× leaner over a full backgammon match. The flashier “20× vs. naive re-send” compares against an implementation nobody ships, and we don't lean on it.
