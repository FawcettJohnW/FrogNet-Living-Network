[SAME_MOVES_REFERENCE_V1]
=========================
On RESP_SAME the proxy moves its response reference exactly as the daemon does. (2026-09-26)

THE DEFECT
----------
The daemon, answering RESP_SAME, sets its response reference for (peer, opcode) to the fields
of the answer the SAME names (daemon/engine/session.py, REQ_REPEAT and REQ_DIFF branches:
new_ref = dyn_vals). The proxy's RESP_SAME branch served the cached body and left its own
reference where it was. Whenever the SAME'd answer was not the proxy's last decoded answer for
that opcode -- two items sharing one template, read A, B, A -- the two references differed, and
the next RESP_DIFF was applied to a reference it was not encoded against. Fields the daemon
omitted as unchanged were filled by the proxy from a different answer. Silent wrong data.

PROVEN on the real code (proxy/test_resp_same_reference_oracle.py: the real
transport_semantic.handle_request against a real daemon SemanticSession and the real template
store on MariaDB; only the socket hop and the origin are substituted):
  A={"id":"A","n":1,"s":"x"}  B={"id":"B","n":2,"s":"x"}   read A, A, B, A (RESP_SAME), then B
  changes to n=1: the daemon diffs against A and omits n; the shipped proxy answered n=2.

THE FIX (proxy/transport_semantic.py, semantic RESP_SAME branch only)
---------------------------------------------------------------------
After serving the SAME'd body, the proxy sets its reference to resp_tpl.extract_dynamic() of
that body -- the same template, the same extraction the daemon used. If the body cannot be
extracted, the references can no longer be made equal: it says so and drops both proxy
references, so the next request is REQ_FULL (which clears the daemon's). The RAW SAME branch in
_handle_raw_and_learn is unchanged: the daemon's RAW SAME does not touch the reference either.

WHY IT MATTERS NOW
------------------
Instance references ([INSTANCE_REFERENCES_V1], the C++ engines, v0.51) keep many instances of one
template, so an answer's SAME is routinely not the last answer decoded. The C++ client has the
same rule; the Python proxy now agrees with it and with the daemon.

GATE
----
test_resp_same_reference_oracle FAILS on the shipped proxy and PASSES on this one. FrogSim
run_all.py: discovery 83/83 and every tier identical before and after (the collectives tier is red
on both only because torch is not installable in the container).


[DISCOVERY_ON_DOT2_ONLY_V1] + [HEALTH_ON_DOT2_V1]
=================================================
All discovery happens on .2. NO FALLBACKS. (John, 2026-09-25)

THE RULE
--------
Discovery and tunnel health probe a node's .2 alias and nothing else. The .1 is
the production address; discovery never installs a probe route to it. When a .2
does not answer, that is the avenue's result: it is logged with the addresses
involved and the avenue produces no candidate. There is no retry on .1.

The incumbency hold is not discovery: it checks an installed winner's .1 over the
winner's own installed route and writes no route. [ROUTE_INCUMBENCY_HOLD_V1] stands.

WHAT WAS REMOVED
----------------
Three paths put probe routes on production .1 addresses. Each began as a rescue
when a .2 did not answer, and the .2 failure was never root-caused because the
rescue hid it every time.

  healthcheck.py      probed <peer>.1: metric-6 /32 dev wgN at the start of every
                      merge. A /32 beats the installed /24, so production traffic
                      to every tunnel peer's .1 rode the probe route until it was
                      deleted. Now <peer>.2.  [HEALTH_ON_DOT2_V1]
  descend.py          [TUNNEL_PEER_HEALTH_EMIT_V1]: a tunnel immediate whose .2
                      did not measure was re-probed srcless on its .1 and emitted
                      as measured. Removed; a silent .2 logs IMMEDIATE_NO_ANSWER.
  descend.py          [PROVE_DOT1_V1] _prove_dot1: when X's .2 did not reflect
                      through an avenue, a /32 to X's .1 was installed through that
                      avenue - LAN clients included - and ping-ponged. Removed; a
                      dark .2 logs PROBE_FAIL plane=.2 x= target= dev= via= src=
                      reason=.

WHY IT MATTERED (Seattle5, 2026-09-25, two merges of ~150 s each)
----------------------------------------------------------------
At 14:59:58-59 the health probe pointed 10.155.155.1, 10.123.123.1 and 10.251.251.1
at probe routes. From 15:01:11 to 15:01:27 _prove_dot1 pointed 10.199.199.1 (the
elected databasehost), 10.251.251.1 (databasehost_control), 10.155.155.1 and
10.123.123.1 at 10.250.250.100 (AI-Host, not a router), then .20, then .85, ~2 s
each. 70 probe installs in two merges. Not one candidate on Seattle5 or BAMacBook
came from a .1 probe that day: every rescue failed, and every one disrupted the
store traffic, the permanent proxy->daemon sockets and every :9009 liveness check
aimed at those addresses while it ran.

WHAT THIS EXPOSES
-----------------
Anywhere a .2 is dark, the node now says so instead of being rescued. Two cases are
on record and were never root-caused:
  - a .2 over a tunnel whose far end returns our identity-src probe by another path
    (NY1 2026-07-14 answered out eth0 via NY2, not back over wg2);
  - a node behind a seg-relay whose .2 the relay did not forward (Seattle2 behind
    Seattle3, 2026-07-10).
Those are defects in the .2 plane, to be fixed there. They are not reasons to probe .1.

GATE
----

test_tunnel_peer_dot2_oracle replaces test_tunnel_peer_health_emit_oracle.
test_behind_relay_dot2_oracle replaces test_behind_relay_pingpong_oracle.
Each fails on the previous tree (the fixtures make every .1 answer, so a rescue
always succeeds there) and passes on this one.


[SAME_IS_BACK_V1] + [SAME_COMPARES_THE_BODY_V1]
================================================
RESP_SAME restored, and the comparison it depends on fixed.

WHY IT WAS GONE
---------------
Not a decision. On 2026-08-02 I was chasing a real bug -- data_cache.py answered
sensors/values from a RAM snapshot loaded once at daemon start, with fresh_s
treated as a filter COLUMN rather than a timestamp predicate, so it matched
nothing and returned authoritative empty arrays. A staleness bug in one file.

My fix was [NO_CACHES_V1]: remove every cache in the system. That took out
data_cache, local_read_cache, both semcache_db callers, the SAME body LRU, the
req-hash memo, REQ_REPEAT, and the RESP_SAME emit sites. I then wrote the
proxy's 502 -- "peer is running pre-[NO_CACHES_V1] code" -- which blamed every
node still doing the right thing.

data_cache was later rebuilt properly as [DATA_CACHE_GEN_V2] with a MySQL
generation counter. The reason for the purge went away; the purge did not.

The instruction had been to remove the memory caches that were never cleared.
The template cache was to be kept -- and core/store.py turns out to be
BYTE-IDENTICAL to the pre-purge tree, so it was never removed. My summary of
that session said it was. The summary was wrong.

THE COMPARISON WAS WRONG BEFORE THE REMOVAL
-------------------------------------------
    session.py:818   new_raw_hash = hashlib.sha256(sem_resp).digest()

sem_resp is the SEMANTIC REPLY -- execute()'s docstring calls it
semantic_reply_bytes. It is diff-encoded against the reply reference, so the
SAME response body produces DIFFERENT bytes whenever the reference moves: after
a reference update, a REQ_MISS, a reconnect, or on another peer. The hash
differed although the response had not changed, so RESP_SAME was missed and a
full DIFF went out instead.

That is why SAME survived at a low steady rate and vanished under a burst -- a
burst churns the reference, so the encoding moved on nearly every request.

The RAW path in the same file always did it correctly:

    session.py:915   new_raw_hash = hashlib.sha256(resp_body_bytes).digest()

Both wrote the same `raw_hash` column and compared against the same
old_raw_hash, so the two paths disagreed about what that column meant.

THE FIX
-------
response_body_hash(dyn_vals, status) -- dyn_vals is the engine's extracted field
values, the response itself, before any encoding. Canonical:
  * SORTED by field name. field_order belongs to the template and shifts when a
    template is re-learned; order sensitivity would reintroduce the same false
    difference in a new place.
  * value via repr, so 1, "1" and 1.0 do not collide.
  * status folded in, so a 200 and a 500 carrying the same text are not "the
    same response".

Applied at ALL FOUR sites -- both REQ_FULL writers and both REQ_REPEAT
comparisons. Writers and comparison must hash the same thing or SAME can never
match; the old code had a comment at one writer reading "Hash the FULL-encoded
response for SAME/DIFF comparison", which is the bug stated as intent.

RESTORED, PORTED NOT REVERTED
-----------------------------
transport_semantic.py has GROWN 2435 -> 2682 lines since the purge and carries
months of later fixes, so the deleted pieces were ported into the current file:
  * _SAME_LRU_MAX / _same_lru / _same_lru_get / _same_lru_put  (bounded, 256 by
    default, oldest-first eviction -- it was never one of the unbounded ones)
  * _serve_from_same, LRU then MySQL, with [SAME_MISS_AUTORETRY_V1] falling
    through to the raw path on a miss instead of 503ing
  * both OP_RESP_SAME branches, which had been 502s
  * the REQ_REPEAT decision (semcache_db.is_req_seen) -- REQ_REPEAT is what
    makes RESP_SAME reachable at all
session.py: _reexecute_semantic and _reexecute_raw restored, with the hash fixed.

Both semcache_db modules survived the purge intact (764 and 651 lines) -- only
their callers were removed -- so the storage layer needed no work and the API
(ensure_table, close_thread_conn, lookup_for_repeat, upsert, upsert_raw,
is_req_seen, get_raw_by_sameid) is unchanged.

GATE
----
test_resp_same_oracle.py -- 12 assertions.
  Current deployed tree: 0/12.  This rev: 12/12.
  FROGNET_OLD_TREE=<pre-purge tree> also asserts the before-state.
The no-site-hashes-the-encoding check is AST-based: response_body_hash's own
docstring quotes the bad line as the thing it replaces, and a text search cannot

DEPLOY BOTH SIDES TOGETHER
--------------------------
A daemon emitting RESP_SAME to a proxy that still 502s it breaks every repeated
request. session.py and transport_semantic.py go out together, every node.

Nodes still on the purge build answer RESP_DIFF and keep working; nodes on this
build answer RESP_SAME to each other. A mixed pond degrades to DIFF rather than
failing -- but only if the OLD proxies never receive a SAME, which means the
daemon side must not go out ahead of the proxy side.
