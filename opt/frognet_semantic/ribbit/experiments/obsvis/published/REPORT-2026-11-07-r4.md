# Observer visibility: direct, server-relayed and FrogNet shared-RAM communication: results

Build obsvis-2026-11-06-r3. Analysis obsvis-analyze-2026-11-06-r4. Run on kernel(s) 6.18.44-fc-v242, 6.18.44-fc-v300, 6.18.44-fc-v310.

## What ran

Eight participants (p1..p8), a server (srv), a controller (ctl) and a router (rt), each in its own Linux network namespace with its own stack, joined in a star through rt. Each participant follows 3 of the other 7, drawn from the seed: 24 true edges among 56 ordered pairs. The attackers try to recover that graph.

Every step of a run was coordinated through a separate control region, a chat-ram of its own in ctl, left out of every capture. Each namespace's agent advertised itself and took every instruction on one held read. Every result came back as tuples: ground truth, the operation logs and the capture headers.

The five conditions used the same machines and the same seeded schedule:

- **A:** direct TLS 1.3, producer to each follower.
- **B:** Mosquitto 2.0.18, topic `chat/<recipient>`, TLS 1.3.
- **C:** chat-ram (chat-ram chat 1.0 (ribbit-platform 0.71)), the chat example's own schema and client, `ChatServer.<recipient>.<producer>`.
- **D:** chat-ram on ribbit::Space (the publish/subscribe library the MQTT and Redis conversions use), own truth: each producer writes its own ring cells, `Chat.<producer>.<producer>.<n mod 64>`; each consumer holds one standing follow per producer it follows.
- **D-all:** the same library, read-all: `Chat.Out.<producer>.<n mod 64>`; each consumer holds one standing follow on `Chat.Out` and filters locally.

C, D and D-all ran over wireguard-go v0.0.20230223 tunnels from each participant to srv.

Seeds 1-6 trained the attackers; seeds 7-10 were held out. Each run lasted 2.0 minute(s).

Versions:

- bed: `obsvis-bed-2026-11-06-r2`

## Observers

- **O1:** p1's link, from a tcpdump capture of headers only (`-s 96`). Scored on the 14 pairs that involve p1.
- **O2:** srv's link, captured the same way. Scored on all 56 pairs. A has no server, so O2 sees nothing for A.
- **O3:** the server operator. For C, D and D-all, this is the operations the host decodes, logged at the client library boundary: chat-ram has no operation trace hook. For B it is Mosquitto's own log (`log_type all`). Scored on all 56 pairs.
- **O4:** p1 as an authorized insider, reading the whole service. Scored on the 42 pairs without p1.

**Attacker:** a logistic regression on lagged per-pair features. The features are timing at w of 10 ms, 50 ms, 200 ms, 1 s and 2 s, packet-size bins, and the keys each observer can read. It was trained on the training seeds and scored on the held-out ones.

**Metric:** AUC, with a 95% bootstrap CI over 1000 draws that resample seeds, then pairs within each seed. Timing correlation alone, with w chosen on the training seeds, is reported beside it.

## Deviations from the brief, and notes

- **Run length.** Each run here lasted the minutes given above; the brief specifies 30. `./matrix.sh 30` runs the brief's matrix unchanged.
- **netem delay and loss: not run.** The kernel these runs used has no `sch_netem`, so those stress phases fail at their first step. They run unchanged on a kernel that has it.
- **H4: not run.** The Ribbit wire has no padding flag.
- **D and D-all are built on ribbit::Space** (`space_c.cpp`, a C ABI over `ribbit_space.hpp`), the one publish/subscribe library the platform's MQTT and Redis conversions use, in place of the brief's small shim.
- **O3 for C, D and D-all is logged at the client library boundary.** chat-ram has no operation trace hook; the log records exactly the operations the host decodes, and nothing the host would not see.
- **O1 in the relayed builds (0.57 everywhere).** p1's link carries only p1's tunnel or broker connection, so the attacker's only usable feature is the pair's direction (p1 producing or p1 consuming). 0.57 is that base rate: it says nothing about which peer. Precision at top-k is the same 0.57.
- **B's p95 latency (about 40 ms) is Nagle's algorithm in the MQTT clients.** 6.5% of B's deliveries take 39-43 ms, Linux's delayed-ACK minimum; the rest take under 2 ms. Measured on chat seed 7 (1 minute): Mosquitto's `set_tcp_nodelay true` alone leaves p95 at 41.8 ms; with TCP_NODELAY also on the paho clients' sockets, p95 is 1.4 ms. B is reported as stock (both defaults); `OBSVIS_B_NODELAY=1` reproduces the comparison.
- **Revocation.** The others' delivery after p8 is revoked is 100% in every run; p8 receives nothing after the revocation, in C, D and D-all alike.
- **Platform bug found: a bag field named `rows` comes back wrapped.** semtpl.hpp's `rebuild_json` special-cases a top-level `rows` (a port of Python's template_utils). The harness's result chunks use `items` instead. Not fixed here: it is wire behavior shared with the Python side.
- **Earlier held-read build (before the rebuild on ribbit::Space).** In a D-all smoke run built on plain held reads, every consumer stalled after p8 was revoked. Identical held reads may be coalesced and tied to the revoked session. Not confirmed, and not present with Space follows (the others received everything).
