WHAT IT IS
  The CroakOS protocol layer. A Role is a service; the name before "Host" in its memory's name is the Role
  (unitsHost.exercise is the Role "units"). Each Role's traffic has its own protocol (tcp, chorus, openqasm) and its
  own encryption, set by that Role's owner in one tuple in the ControlRam, (channel, setting, <Role>).
  No key is stored. A node computes the key it sends a Role's traffic under:
      the first 32 bytes of HMAC-SHA384(the Role's secret on the machine, this node's FNID, the Role's name,
      the number in the setting)        (SHA-384 from update 20261122f; SHA-256 before it)
  The number is random and its owner sets it. A switch of key is the number changing.
  A frame that does not open is not tried under any other key: it goes back and is sent again.
  The design: opt/frognet_semantic/docs/PROTOCOL-LAYER-DEMONSTRATION-WALKTHROUGH-AND-DESIGN-v0.5.md (in this file set).

WHAT IS IN THE TARBALL
  The runtime files under opt/frognet_semantic (core, daemon, proxy, agent_workload) and usr/local/frognet-ai that
  differ from main (948b435), core/channel_admin.py, the design document and this note. One tarball, the same for

  One file of main is no longer used and is not removed by a tarball:

EVERY NODE GETS IT
  Install it on every node of the network. A node with this build and a node without it have not been run against
  each other.

A NODE'S SETTING FILE
  A node with no /etc/frognet/semantic_transport, or whose file says tcp, keeps its traffic on its TCP sessions: no
  frame, key or channel setting of this layer applies to it. (The proxy's and the daemon's own handling of the
  semantic wire changed on this branch for every transport; the wire test between machines passes on tcp.)
  To have a node carry Roles' traffic under this layer its file names chorus on one line:
      auto
      databasehost_control.frognet chorus
  (FROGNET_SEM_TRANSPORT_FILE names another file.) Restart the daemon and the proxy after changing it. Every node
  that is to carry a Role's traffic needs it, at both ends of the connection.

THE FILE IS WATCHED (added 22 November; frognet-transport-watch-and-monitor-20261122a.tgz)
  Change /etc/frognet/semantic_transport and the daemon and the proxy are restarted for you, when the file says
  something other than what they read at start. A file they could not start on restarts nothing, and the reason is
  in:   journalctl -u frognet-transport-watch
  The watch starts with the daemon. frognet_monitor shows, under the node's own lines:
      protocol  what the running daemon and proxy read (and what the file says now, if that differs)
      secret    for each Role with a secret on this node, eight hex digits that are the same on every node holding
                the same file

WHAT A NODE NEEDS FOR A SEALED ROLE
  /etc/fnid                               the node's own identity. Every node has it already.
  /etc/frognet/channel_secrets/<role>     the Role's secret, at least 32 bytes, mode 600. The SAME file on every node
                                          that carries the Role's traffic. Placed by you, offline. It is never sent.
  Make it on one node:
      /opt/frognet_semantic/venv/bin/python3 /opt/frognet_semantic/core/channel_admin.py secret <role>
  and copy that one file to the same path on the other nodes that carry the Role.

THE OWNER'S COMMANDS (run on a node that holds the Role's secret; each is one write, and returns when every end
that carries the Role reports it is sending the new way)
      A=/opt/frognet_semantic/venv/bin/python3\ /opt/frognet_semantic/core/channel_admin.py
      $A show
      $A set <role> --protocol chorus          (tcp | chorus | openqasm)
      $A set <role> --seal                     (encryption on: a new random number goes into the setting)
      $A set <role> --new-key                  (a new random number: every sender computes a new key)
      $A set <role> --algorithm chacha20-poly1305
      $A set <role> --unseal
  A protocol and an encryption are not changed in one command.

UPDATE 20261123g (23 Nov 2026): A ROLE'S OWN SECRET MOVES FORWARD; THE NETWORK'S DEFAULT SECRET
  John, 22 Nov 23:48. Two kinds of secret in /etc/frognet/channel_secrets:
    default    the network's. Every Role with no file of its own uses it. It never moves.
               make it on one node:   channel_admin.py secret default     then place the same file on every node.
    <role>     a Role's own. It MOVES FORWARD one step at every key switch of that Role, on every machine that holds it.
  A Role's setting has "step". At a key switch (--seal, --new-key, --algorithm) the command draws a new number and
  raises step by one, in one write. Each machine that sees step s works out secret(s) in memory
  (secret(s) = HMAC-SHA384(secret(s-1), "next", the Role's name, s), once for each step it missed), verifies the
  setting's check under it, and only then writes it over the Role's file and erases the one before. The file is then
      FROGNET ROLE SECRET AT STEP <s>
      <48 bytes>
  WHAT THIS MEANS FOR PLACING A ROLE'S SECRET:
    * place the file as made (step 0) on every node that carries the Role. A node that gets it late catches up by
      itself, however many switches it missed, as long as its file is at a step no later than the setting's.
    * a file copied from a node AFTER a switch is at that node's step; that works too.
    * an earlier secret cannot be got back from a later one, on any node. That is the purpose.
  frognet_monitor shows each secret's hash and, for a moved one, its step:  secret  default 1a2b3c4d   units 9f8e7d6c step 3
  Two nodes hold the same secret when hash AND step are the same.
  What the logs say (journalctl -u frognet-daemon -u frognet-proxy | grep A_ROLES_OWN_SECRET):
      units: the setting is at step 3 and this machine's secret was at step 2: moved forward 1 step(s), written over
      the Role's file, and the earlier secret erased (hash ...)
      ... another process of this machine had already written it          (the daemon and the proxy both see it)
      a setting for units is IGNORED: step 2 is lower than the step this machine's secret for 'units' is at (3)
      a setting for units is IGNORED: its check does not verify against this machine's secret for units at step 3
  A node that does not hold a Role's own secret ignores that Role's setting; channel_admin.py lists such ends as
  "IGNORED it" and does not wait for them.

UPDATE 20261123l (23 Nov 2026): THE FRAME RIDES THE WIRE SOCKET; A HOLD THAT ENDED IS HELD AGAIN
  John, 08:40: "Why are we sending the protocol for Chorus over a separate socket? It should be multiplexed onto the
  wire socket." 08:42: "What goes on the physical wire is a TCP data packet. What is in that packet is mine. The
  packet is created by the protocol handler to be placed on the wire. On the other side, the sniffer says this is a
  Chorus packet and ships the frame to the Chorus handler."
  WHAT WAS BUILT BEFORE: the daemon sniffed the first word of a CONNECTION, so the frame had a connection of its own.
  Since build j a node told `auto` held that connection BESIDE its wire session to the same daemon port.
  NOW [THE_FRAME_RIDES_THE_WIRE_SOCKET_V1], on a node that was not told chorus:
    * toward the daemon, each of the frame layer's packets goes on the wire session's socket behind the 4 bytes
      FRM\x02. The daemon's reader sniffs EACH packet: one that begins so is handed to the frame handler, takes no
      request number, and is answered by nothing. Every other packet is returned exactly as before.
    * toward the node, each rides the session's return channel numbered 0xFFFFFFFD, through the session's one
      writer, as a held read's fire already rides it (0xFFFFFFFE).
    * no connection is opened for the frame. When the wire session ends, what rode it ends with it, and rides the
      next session when there is next something to send.
    * inside the frame nothing changed: each packet carries its protocol's word (tcp, chorus, openqasm) and is handed
      to that handler; sealing, keys, switches, fires are as they were.
  The journal says it once per destination:
      [THE_FRAME_RIDES_THE_WIRE_SOCKET_V1] this layer's packets for 10.250.250.1:9009 ride the wire session to it; no
      connection is opened for them
      [THE_FRAME_RIDES_THE_WIRE_SOCKET_V1] the wire session from 10.123.123.1 carries this layer's packets (1); ...
